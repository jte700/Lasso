# Current limitations

Lasso runs a local Node.js service and offers a browser interface and a native macOS app. These are the current implementation boundaries.

- **Identity and access:** the default server listens on `127.0.0.1`. Local actor fields and the identity switcher record attribution; they are not an authentication or authorization boundary. A hosted deployment needs a separate access-control design.
- **Sharing:** generated source links depend on a reachable running server. Setting `SHARE_BASE_URL` changes link construction; it does not deploy the service or create a tunnel. Sharing selected evidence is separate from project synchronization.
- **Collaboration:** snapshots and mutations use optimistic conflict checks, but there is no remote directory synchronization or automatic merge service.
- **Project selection:** the browser accepts an absolute directory path; the macOS app provides a folder picker and multiple directory toggles. Imports read the directory in place. Markdown/plain-text saves and approved agent edits can write project files.
- **Document editing:** DOCX and PDF text can be extracted and edited as a separate versioned Lasso text layer. Their original bytes and formatting remain intact. Structured DOCX history diffs and exporting a text layer back into the original document format are not implemented.
- **Native writing assistance:** the macOS integration depends on Accessibility permissions and the capabilities of the active editor. Text insertion, caret geometry, and source-link presentation can differ between host applications.
- **Extraction and provenance:** indexing is local and bounded. Unsupported, ambiguous, or unextractable content is not a verified numeric answer. Provenance follows recorded relationships; it cannot recover lineage that was never recorded. Drawing format boundaries are documented in [design-source-indexing.md](design-source-indexing.md).
- **Watching:** watchers run for enabled directories with system attribution; explicit directory actions retain the requesting actor. Project-history deletion is not implemented. Large projects retain original snapshot content as well as indexed metadata; configure index exclusions for generated or unwanted files.
- **Stored file versions:** every recorded version of a file keeps a copy of its bytes, named by the SHA-256 of its content. Files are read and stored a chunk at a time, so recording a large file does not hold it in memory. A file's **current version is always stored uncompressed**, at the path every earlier Lasso build reads. Only text versions (plain text, CSV and TSV, code, JSON, Markdown, XML, YAML, notebooks) that are no longer the current version of any folder, and that no pending agent edit names, are compressed with zstd, when they are between 256 bytes and 16 MB and compressing saves at least a tenth of their size. This runs **by default**, in small batches a minute after captures stop and never during one (each batch stops once it has read about 32 MB or spent about 100 ms, after at least one file, since compressing shares the server's thread with suggestions), and leaves alone anything stored or found again by a capture in the last 10 minutes. The compressed copy is written through a temporary file and read back and checked against its hash before the uncompressed one is removed. Workbooks, Word files, decks, PDFs, pictures, video and drawings are never compressed. A compressed version that becomes current again (a file goes back to older content, or another folder has the same bytes) is stored uncompressed again. It is switched off with `LASSO_BLOB_COMPRESSION=off` (or `blobCompressionEnabled: false` in the server config); copies already compressed stay readable. An earlier build sharing the data folder reads current versions as before, but cannot show diffs or open old text versions that were compressed. Before running an earlier build against the data folder, quit Lasso (or start it with `LASSO_BLOB_COMPRESSION=off`) and run `npm run blobs:decompress -- --data-dir <data folder>` (or `node scripts/decompress-blobs.mjs <data folder>`), which turns every compressed copy back into an uncompressed one. It is safe to stop and run again, and a second run changes nothing.
- **Releasing old versions' bytes (retention):** available and **off by default**, because released bytes cannot be brought back. It is switched on with `LASSO_BLOB_RETENTION=on` (or `blobRetentionEnabled` in the server config); with it off nothing is ever released. When on, it runs in small batches after captures stop, never during one, and a version keeps its bytes while any of these holds: it is among its file's newest 10 versions (`LASSO_BLOB_RETENTION_VERSIONS`); it was its file's content within the last 30 days (`LASSO_BLOB_RETENTION_DAYS`); it is in the current version of any folder; it is in a version that a share link, a linked claim (its source and its document), a provenance link or a pending agent edit points at; evidence shown to an agent, an agent's bound field or a document edit layer names it; its folder is on a removable drive; a version of the folder holding it has no index; or it was stored, or found again by a capture, within the last 6 hours (and never less than 10 minutes, so a second Lasso sharing the data folder is never undercut part way through a capture). A released version keeps its place in the timeline, its events and its recorded values: a source preview (`/api/dependency-objects/:id/preview`, and a linked claim's preview and viewer) answers with the recorded value and a `bytesReleased` field saying the original file was not kept, which the Mac app does not show yet; timeline diffs stored as line runs show their summary without the lines, and "Where did this come from?" leaves that version out of the value history and counts it. Opening, downloading, sharing or applying the original bytes of a released version fails with a message saying they were not kept. Each release is recorded with its time, so a released version is told apart from a damaged store. A version whose index was written by an earlier reader keeps what that index recorded; a newer reader cannot add to it once the bytes are gone. Bytes that no recorded version uses (an agent edit that was never applied, for one) are not released.
- **Derived table data:** the table index (`derived/tables.sqlite`) stores rows a file's versions share once, and removes tables no current, shared or linked snapshot needs (keeping each file's last 3 versions) in small batches after captures. A removed table is read again from its file if it is ever wanted, which needs that version's bytes.
- **Value changes:** suggestions name a value's change only when it happened since the user last accepted its file or within the last 7 days, whichever is shorter. Changes are recorded from this build on; history from before it shows versions without a change kind. Worksheet formula cells read as recalculated rather than edited; cells of very large sheets answered by the table index do not carry that yet. Changed words are marked in text, Markdown and Word passage previews and changed cells in The Ranch's sheet view; PDF passages and The Ranch's PDF and text viewers are not marked yet.
- **Memory:** derived-data caches share one budget (64 MB by default, `LASSO_CACHE_MB`) and shrink to 8 MB after a minute without requests. After an index pass that read at least 64 KB of changed files, a full garbage collection runs, which adds a few milliseconds to large edits.
- **Rolling back to an older build:** builds before this one cannot read row keys written by reader 9 for links made since, or text versions stored compressed. Run `npm run blobs:decompress -- --data-dir <dir>` before running an older build against the same library.
